# TitovStroy — память проекта (для Claude)

> Читается автоматически в начале каждой сессии. Держим только то, что реально стоит токенов:
> жёсткие правила, окружение/доставка, неочевидные ловушки. Фичи и их детали — смотри в коде
> (там комментарии на месте) и в `git log`, не дублируем это сюда. Общение — по-русски, кратко.

## Что за проект
CRM для ремонтно-отделочной компании «TitovStroy» (Казахстан). React + Vite + Firebase Realtime Database.
Логика — в `titovstroy/src/App.jsx` (~13 000 строк) + `titovstroy/src/production/ProductionModule.jsx`
(модуль производства, встраивается в «Объекты» через `<ProductionModule embedObjectId embedTab clientInfoCard/>`).
Хранилище — обёртка `storage` (Firebase RTDB + localStorage-резерв), ключи `titovstroy-*`.
Firebase-ключи санитизируются: всё кроме `[a-zA-Z0-9_]` → `_` (вложенные пути через `/` не работают).

## Окружения — ВАЖНО
- **Прод**: Firebase-проект `titovstroy-da1cf`, ветка `main`. Нет `VITE_FB_*` → код берёт зашитый `_FB_PROD`. Без метки «🧪 ТЕСТ».
- **Dev**: своя Firebase-база + ветка `objects-refactor` → Vercel Preview, `VITE_FB_*` заданы → `IS_DEV_ENV=true`, метка «🧪 ТЕСТ · dev-база».
- `firebaseConfig = IS_DEV_ENV ? _FB_ENV : _FB_PROD`. Боевую базу и `main` не трогаем без подтверждения владельца.

## Доставка изменений
`git push` в этом окружении заблокирован (403) — и обычный git, и GitHub API (create_branch/push_files
через MCP тоже 403 «Resource not accessible by integration»). Единственный рабочий путь:
1. Правим код, собираем (`npx vite build` должен проходить), гоняем `npx vitest run`.
2. Отдаём изменённые файлы владельцу через `SendUserFile` — он сам заливает на GitHub
   (Add file → Upload files, перетащить файлы по тем же путям — заменяет, не дублирует).
Коммиты локально делаем для истории; «Unverified» на GitHub — норм, не подписать и не запушить всё равно.

## ЖЁСТКИЕ ПРАВИЛА (нарушать нельзя)
1. **Юридический текст документов (договоры, приложения, акты) не менять ВООБЩЕ.** Только данные/вёрстка вокруг.
2. **Клиенту НИКОГДА не показывать себестоимость, маржу, подрядчиков, внутренние заметки.**
   Клиентские страницы: `PublicProgress`, `publishDocs`, `estimateToClientHtml` — только клиентские цены.
   Договоры подряда (`podryad`/`podryad_annex`) клиенту не уходят и в Финансы-проекты не идут (это себестоимость).
3. **Ничего не должно теряться.** `saveListProtected` — мердж по id/objectId, бэкапы, блок «пусто поверх». Не ломать.
4. Перед мержем dev→main или другими рискованными операциями с боевой базой — **экспорт JSON (бэкап)**.
5. **ТАБУ (владелец, категорично): НЕ ТРОГАТЬ текущие боевые данные** в разделах Финансы, Производство,
   Сметы, Договоры, АВР/акты, Клиенты, Подрядчики. Никакой код не должен АВТОМАТИЧЕСКИ менять/
   переписывать эти данные на боевой базе (в т.ч. авто-миграции, авто-нормализации, авто-синки,
   которые пишут). Любое изменение этих данных — только по явному действию владельца и только после
   его подтверждения. Новые механизмы (напр. команды производства этапа 2А/2Б) до полной приёмки —
   ТОЛЬКО на dev-базе (Preview с `VITE_FB_DATABASE_URL`), в `main`/боевую не заливать.

## Неочевидные ловушки (сюда стоит заглянуть перед правкой статусов/производства)
- **`unifiedStatusOf(o)`**: статус объекта для ОТОБРАЖЕНИЯ/фильтра — если у объекта есть карточка
  производства со статусом active/paused/done/cancel, он ПЕРЕВЕШИВАЕТ `object.status` (нужно для старых
  объектов, где реальный статус исторически жил в производстве). Кнопки статуса на карточке объекта
  пишут `object.status` через `saveObjField`, который ЗЕРКАЛИТ выбор в `production.prodStatus`
  (`DEAL_TO_PROD`) — если этого не сделать, клик по кнопке визуально ничего не меняет (уже дважды
  ловили этот баг). `computeIssues` и «signed→финпроект» смотрят на сырой `object.status`.
- **Финпроект заводится** авто при статусе «Договор подписан» (`saveObjField`, СНАЧАЛА создаёт
  финпроект+производство, потом меняет статус — иначе при сбое сети объект зависает «подписан» без них),
  либо вручную («💰 В финансы»/«В проект»/«+ Проект»). Ключ проекта — номер основного договора.
- **Облако**: если SDK (WebSocket) не отвечает — есть REST-фолбэк (`_fbRestSet`/`_fbRestGet`) на тот же
  ключ через HTTPS. Баннер «облако недоступно» гаснет сам, когда `dirtyKeys()===0`.
- **Запись списков — единая очередь по ключу**: `saveListProtected` = чтение→слияние→бэкап→запись, НЕ
  атомарно. Обёртка сериализует вызовы одного ключа (цепочка промисов в `_saveQueues`), иначе два
  параллельных сейва одного ключа затирают друг друга. Производство больше НЕ использует эту
  обёртку: только granular-команды внутри Firebase transaction. Прод-карточка: очередь правок в
  module-scope ProductionModule, flush — цикл-до-сходимости, single-flight через Map промисов
  (`flushPendingProduction()` реально ждёт записи, включая resolve-change).
  **2Б завершён:** каждое изменение карточки ДО обновления UI синхронно сохраняется в per-user
  `titovstroy-production-draft-v2:*` с `{base,local,ensure,rev,changeId}`; `startProductionSession`
  поднимает его после reload/crash только для того же uid. Подтверждение удаляет draft только если
  его revision не новее отправленной. Фоновые `bg_*` команды ДО постановки в App-очередь сохраняются
  в `titovstroy-production-retry-v1:<uid>` и повторяются после входа; каждая постановка имеет
  `__draftRevision`, поэтому поздний успех старой команды с тем же changeId не удаляет новую.
  Replay идемпотентен. Удалённая на другом устройстве карточка не воскрешается автоматически:
  владелец явно выбирает «восстановить / принять удаление».
  Массовый restore блокируется при наличии ЛЮБОГО валидного production draft/retry на устройстве,
  включая записи другого uid: иначе старый пользователь позже вошёл бы и применил команду поверх
  уже восстановленной базы.
  ЛЮБОЙ выход из сессии — ТОЛЬКО через `endSessionSafely` (App): 1) `_prodEndingRef=true`
  (новые bg_ отвергаются — `isBlockedWhileEnding`; ретрай-таймер молчит); 2)
  `flushAllProductionPending()` (module-очередь + bg_-ретраи с `__retryFlush` + СТАБИЛИЗАЦИЯ
  хвоста `_prodQueue` циклом `awaitQueueSettled`) И `storage.flushDirty()` (сметы/финансы тоже!);
  3) не ушло — confirm (кнопка) / alert (принудительный после смены пароля); при подтверждённой
  потере `storage.discardOwnDirty()` — СВОИ (uid+tab из маркера `{ts,uid,tab}`) dirty-записи
  удаляются ЦЕЛИКОМ (метка+значение+`__wts`+`_mem`), иначе следующий пользователь получил бы
  локальную копию (getResult) и отправил бы «потерянное» в облако; чужие вкладки не трогаются
  (`isOwnDirtyMarker` СТРОГИЙ: legacy-маркер без владельца — НЕ свой). `flushDirty`/«Повторить»/
  авто-флеш шлют ТОЛЬКО свои (`dirtyKeysFlushable`); legacy — строгий карантин (не читается,
  не отправляется и не снимается обычной новой записью; виден в баннере и выгружается отдельным
  recovery JSON). Успешная запись снимает только СВОЮ метку (не гасит чужую вкладку).
  Глобальный `dirtyKeys()` остаётся ТОЛЬКО в restore-guard (намеренно) и баннере legacy.
  4) инкремент `_prodAppSession` (команды в очереди не выполняются — проверка ДО
  транзакции; поздние ответы не трогают state) + `stopProductionSession()`. Прямой
  `setCurrentUser(null)` запрещён. changeId `cm_<objId>` / `bg_*` (учёт неудач —
  `accountProductionFailure`: конфликт bg_ снимает id полностью, иначе баннер зависает).
  cloudError гасится ТОЛЬКО когда чисто везде (unsynced производства + dirtyKeys storage);
  баннер: `cloudError || prodUnsyncedN>0 || dirtyCount>0 || legacyDirtyN>0`.
- **EDITOR-LOCK «одна вкладка редактирует»** (вместо общего черновика для нескольких вкладок):
  основной механизм — браузерный Web Locks API (`titovstroy-editor`, exclusive, ifAvailable).
  Для браузеров без Web Locks — fallback lease с fencing-token:
  `titovstroy-edit-lease` = `{uid,tab,token,heartbeatAt}`, heartbeat 5с, TTL 30с и обязательная
  write-then-verify проверка. Отсутствующий/протухший lease означает лишь «можно попробовать
  захватить», но НИКОГДА не даёт права записи сам по себе. Оболочка `EditorSessionGate` захватывает
  lock ДО монтирования MainApp; без lock MainApp монтируется в строгом read-only, а содержимое
  редакторов `inert`. Публичные КП/кабинет lock не захватывают и не гейтятся.
  ЦЕНТРАЛЬНЫЙ fail-closed гейт `_writeGateFail()` стоит ДО любых побочных эффектов во всех путях
  записи: `storage.set`/`setCloudOnly`/`mutateTransaction`/`flushDirty`/`_appendAuditEntry`/
  `mutateProductions` (+ массовый restore). Каждая начатая запись учитывается как in-flight:
  logout/смена редактора удерживает lock до её завершения, а номер editor-сессии проверяется
  после await, поэтому поздний ответ прежней вкладки не меняет localStorage, `_mem` или React-state.
  `getResult` при ЧУЖОМ или legacy dirty-маркере (`mayUseLocalCopy`) не использует НИ ОДИН локальный
  источник (кеш 30с, dirty, фоллбек, `_mem`) — только Firebase, иначе `unavailable`.
  `set()` при чужом черновике НЕ пишет localStorage. После получения lock новый tab того же uid
  принимает structured dirty закрывшейся вкладки (`adoptUserDirty`) и дожимает его; чужой uid и
  legacy не принимает. Lock отпускается при безопасном logout, pagehide/beforeunload и размонтировании
  оболочки; pagehide сразу переводит оставшийся в bfcache интерфейс в read-only.
  Конфликт (элемент удалён с другого устройства) — `rebaseLocalProduction` + confirm
  «восстановить/принять удаление». `viewer` вообще не захватывает editor-lock и остаётся в строгом
  read-only; в производстве запрет продублирован в `patchProd` (не только визуал).
  Старые production-элементы без `id` НЕ мигрируются при открытии. При первой ЯВНОЙ правке карточки
  `normalize-card-ids` и сама правка идут одним атомарным batch; content-based id не зависит от
  позиции строки, поэтому удаление/перестановка на другом устройстве не направляет patch в соседа.
  Дубли существующих id целиком переводятся на content-id. Прод-wide `normalize-ids` на боевой
  по-прежнему запрещён и гейтится `IS_DEV_ENV`.
  `mutateTransaction`: первый прогон runTransaction на холодном кеше даёт null ДАЖЕ при данных на
  сервере — abort нельзя, возвращаем текущее «[]», CAS дожмёт реальные данные; SDK ПЕРЕЗАПУСКАЕТ
  колбэк — результат прогона сбрасывать каждый раз (`createTxnApplier`, не убирать).
  ТАБУ-гейты (до приёмки 2А, все `IS_DEV_ENV`): авто-синк этапов, autoCreate карточки при
  открытии, авто-импорт клиентских замечаний; на боевой пишут только явные действия владельца.
- **Гонка первичной загрузки**: флаги `_*Loaded` — refs (не ре-рендерят). Авто-синки зависят по
  массивам, поэтому в deps добавлен `loadedTick` (инкремент в конце каждой загрузки), иначе синк
  не перезапустится, если его данные догрузились позже. Новые синки — тоже с `loadedTick` в deps.
- **App Check**: инициализируется ТОЛЬКО при `VITE_RECAPTCHA_SITE_KEY` И `VITE_APPCHECK_ON="1"`.
  Ключ на проде задан, но домен не зарегистрирован → был 403 + 24ч блок reCAPTCHA (Enforce на RTDB
  выключен, защиты 0). Прежде чем включать (`VITE_APPCHECK_ON=1` + Enforce) — зарегистрировать
  домены titovstroy.kz/www в reCAPTCHA admin и Firebase App Check, проверить по метрикам.
- **Роли и права**: пресеты и валидация живут в `utils.js` (`DEFAULT_ROLE_PERMISSIONS`),
  сохранённая матрица — отдельный ключ `titovstroy-role-permissions`. Настройка в
  «Админка → Права ролей»: для разделов `none/own/all`, отдельно права редактирования,
  Финансы и показ детальных финансовых результатов. `admin` всегда принудительно полный,
  чтобы нельзя было заблокировать систему. `sales_head` по умолчанию видит все объекты и
  общую аналитику, но не себестоимость/прибыль/маржу/долги и ничего не редактирует.
  `user` (замерщик) видит главную, объекты и аналитику только по своим данным.
