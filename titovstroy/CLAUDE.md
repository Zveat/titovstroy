## Что за проект
CRM для ремонтно-отделочной компании «TitovStroy» (Казахстан).
Стек: **React + Vite + Firebase Realtime Database**. Почти вся логика — в двух файлах:
- `titovstroy/src/App.jsx` (~12 000 строк) — основное приложение;
- `titovstroy/src/production/ProductionModule.jsx` — модуль производства (встраивается в «Объекты»).

Хранилище — обёртка `storage` (Firebase RTDB + localStorage-резерв), ключи вида `titovstroy-*`.
Ключи в Firebase санитизируются: любой символ кроме `[a-zA-Z0-9_]` → `_` (вложенные пути через `/` НЕ работают).

## Окружения (dev / prod) — ВАЖНО
- **Боевая база**: Firebase-проект `titovstroy-da1cf`, ветка `main`, боевой домен. У прода НЕТ переменных `VITE_FB_*` → код берёт зашитый `_FB_PROD`. Метки «🧪 ТЕСТ» на проде нет.
- **Dev**: отдельная тестовая база Firebase + ветка `objects-refactor` → Vercel Preview
  (`titovstroy-git-objects-refactor-zveats-projects.vercel.app`, НЕ иммутабельный hash-URL).
  На превью заданы `VITE_FB_*` (dev-база) → `IS_DEV_ENV=true`, внизу слева метка «🧪 ТЕСТ · dev-база».
- Конфиг: `_FB_PROD` (прод, зашит) / `_FB_ENV` (из `VITE_FB_*`). `firebaseConfig = IS_DEV_ENV ? _FB_ENV : _FB_PROD`.
- **Вся разработка идёт на dev-ветке. Боевую базу и `main` не трогаем**, пока владелец не подтвердит мерж.

## Доставка изменений
`git push` в этом окружении заблокирован (403). Поэтому:
1. Правим `App.jsx` / `ProductionModule.jsx`, собираем (`npx vite build` должен проходить).
2. Отдаём файл владельцу через чат (он сам заливает на GitHub в ветку `objects-refactor`).
3. Vercel сам пересобирает превью.
Коммиты локально делаем (для истории), но «Unverified» на GitHub из-за отсутствия GPG-подписи — норм, подписать нельзя, и push всё равно закрыт.

## ЖЁСТКИЕ ПРАВИЛА (нарушать нельзя)
1. **Юридический текст документов (договоры, приложения, акты) не менять ВООБЩЕ.** Только данные/вёрстка вокруг.
2. **Клиенту НИКОГДА не показывать себестоимость, маржу, подрядчиков, внутренние заметки.**
   Клиентские страницы: `PublicProgress`, `publishDocs`, `estimateToClientHtml` — только клиентские цены.
   Договоры подряда (`podryad`/`podryad_annex`) клиенту не уходят и в Финансы-проекты не идут (это себестоимость).
3. **Ничего не должно теряться.** Есть защита `saveListProtected` (мердж по id, бэкапы, блок «пусто поверх»). Не ломать.
4. Перед мержем dev→main — **экспорт JSON боевой базы (бэкап)**.

## Ключевая механика (текущее состояние)
- **«Объекты» и «Производство» ОБЪЕДИНЕНЫ** в один раздел. Пункт меню «Производство» убран.
  Карточка объекта = вкладки: Информация · Документы · Запуск · Этапы · Финансы · Журнал · Замечания · Сдача.
  Производственные вкладки рендерятся встраиванием `<ProductionModule embedObjectId embedTab clientInfoCard/>`.
- **Статусы — единые, 9 штук** (`DEAL_STATUSES`): new, approval, signed, refuse, work, paused, done, cancel, archive.
  Мастер — `object.status`. `unifiedStatusOf(o) = o.status`. Никаких переопределений из производства/финансов.
- **Как проект попадает в Финансы → Проекты**:
  - авто: объекту ставят статус «Договор подписан» (`signed`) → `saveObjField` заводит финпроект (+ карточку производства), если его ещё нет;
  - вручную: кнопка «💰 В финансы» на договоре ремонта (`startFinProjFromObject`); у доп. соглашения — «💰 В проект» (не плодит дубль, обновляет бюджет основного проекта);
  - вручную: «+ Проект» внутри Финансов.
  - Ключ проекта — номер основного договора (`contractNo`). Один осн. договор = один проект.
- **Авто-синки (без кнопок, дебаунс, защищены флагами загрузки)**:
  - бюджет финпроекта = основной договор + все доп. соглашения (эффект по `[contracts]`);
  - этапы производства ← сметы объекта (эффект по `[estimates]`), сметные этапы помечены `fromEst`, ручные не трогаются;
  - ПЛАН объекта = сумма всех смет объекта.
- **Справочник подрядчиков**: Админка → вкладка «🔨 Подрядчики» (реестр `workers`, ключ `titovstroy-workers`).
  Договор подряда (`type:"podryad"`) ссылается на `workerId`. Кнопка «+ Приложение» на договоре подряда = логика «один договор → приложения на каждый объект».
- **Сессии/доступ**:
  - логин пишет в сессию `authAt` (время входа); смена пароля ставит на юзере `pwChangedAt`;
    при загрузке сессия, вошедшая до смены пароля, разлогинивается; тот, кто меняет пароль (в т.ч. свой), себя не выкидывает;
  - presence («был в сети»): каждый пишет СВОЙ ключ `titovstroy-presence-<id>` (без чтения-записи общего блока, чтобы отметки не затирались); админ читает по ключам всех пользователей + старый общий блок для совместимости.

## Роли (уточнено)
admin (полный доступ), manager (финансы readonly), foreman (прораб), user (замерщик), viewer (только чтение).
Финансы по ролям:
- **admin/manager** — видят финансы везде (manager — readonly).
- **foreman (прораб)** — видит финансы ТОЛЬКО ВНУТРИ объекта: вкладка «Финансы» объекта + финблок карточек (долг/расходы/маржа). Сам раздел «Финансы» ему закрыт (effScreen редиректит). Финданные ему теперь грузятся (`loadFinance` для admin/manager/foreman).
- **user (замерщик)** — финансы (себестоимость/маржа) ТОЛЬКО в смете при заполнении, больше НИГДЕ: его Главная — «Мои задачи» (без финKPI), финблок карточек и вкладка «Финансы» объекта закрыты, финданные не грузятся. Пункт меню «Финансы» есть, но внутри — пометка «доступ закрыт».
- **viewer** — только чтение объектов.

## Новые экраны (панели проблем + календарь)
- **Детектор проблем**: `computeIssues(data)` в `src/utils.js` — чистая read-only функция, покрыта тестами. Возвращает проблемы с `scope: "today"` (операционные) / `"check"` (целостность данных). Презентация — `<IssuePanel/>` (module-level в App.jsx).
- **«Что горит сегодня»** — вверху Главной у admin/manager (просроченные этапы, объект без прораба, подписан без финпроекта, долг, замечания клиента, скоро сдача). Клик → карточка; «до завтра» скрывает (localStorage `titovstroy-issue-dismissed`).
- **Главная «Мои задачи»** — у прораба И замерщика: те же операционные проблемы по ИХ объектам, БЕЗ финансовой группы.
- **«Проверка базы»** — вкладка в Админке (admin): дубли договоров, сироты, пустые production-карточки, подряд без рабочего, расхождение бюджета/смет, платежи без договора, клиенты без имени/тел, ссылки без срока. Вердикт 🔴/🟡/🟢. Read-only.
- **📅 Календарь производства** (`screen==="calendar"`, admin/manager/foreman) — общий таймлайн этапов по объектам / по прорабам, окно 2нед/месяц/3мес, подсветка просрочек и перегруза бригад (`buildCalendarStages`/`foremanLoad` в utils, тесты есть), клик по этапу → вкладка «Этапы» объекта. v1 read-only; drag-drop / инлайн-отметка / назначение прораба — не сделано (следующий заход).

## Журнал изменений (audit log)
- **Логгер** `logChange(user, ev)` (module-level, App.jsx). Запись: `{ts, userId, by, entity, entityId, label, objectId, field, action, old, new, detail, source}`.
  `entity`: object|contract|estimate|finance_tx|stage|publish|document|client|user. `source`: manual|import|autosync|cabinet.
- **Хранение помесячное, без лимита**: ключи `titovstroy-audit-ГГГГ-ММ` + индекс месяцев `titovstroy-audit-index`. Старый ключ `titovstroy-audit` (кольцо 500) — только читается (архив), больше НЕ пишется. `writeAudit(...)` оставлен как оболочка над `logChange` (обратная совместимость).
- **Что логируется**: статус объекта, сумма/статус договора, создание/изменение/удаление финопераций (оплаты/расходы, с привязкой к объекту по №договора), статус сметы, назначение прораба (объект и этап), сроки этапов (blur-diff в ProductionModule через проп `onAudit`), публикация/закрытие клиентского доступа и переключатели видимости, удаление объекта/договора/клиента. Фоновые авто-republish снимков НЕ логируются (только явные действия).
- **UI** `AuditTab` (App.jsx): общий журнал в Админке → «📋 Журнал» (только админ) — селектор месяца/архива, фильтры по пользователю/разделу, поиск, показ «было→стало» + бейдж источника, экспорт CSV. Тот же компонент с пропом `objectId` = срез по объекту: вкладка «🧾 Изменения» в карточке объекта (только админ).
- **Откат значения** — НЕ сделан в v1 (по решению владельца: сначала копим структурные «было→стало»). Кандидаты на откат: сумма договора, срок этапа, прораб (безопасные поля).

## Бэкап в файл (Админка → 🗄 Бэкапы)
- **Скачать полный бэкап (JSON)** `exportAllJSON` — читает НАПРЯМУЮ из ключей базы (не из того, что подгружено в UI, чтобы бэкап был полным) все разделы: objects, contracts, estimates, clients, contragents, workers, productions, financeTx, financeProjects, reports + financeMeta + catalog. Формат `{_type:"titovstroy-backup", _version, _exportedAt, _env, _counts, data}`.
- **Восстановить из файла (JSON)** `importAllJSON` — проверяет `_type`, проверяет доступность базы (`probe.status!=="unavailable"`), требует ввести «ВОССТАНОВИТЬ» (`confirmTyped`), на боевой базе — доп. предупреждение. Перед перезаписью КАЖДЫЙ раздел уходит в свой `*-backups` (откат возможен), затем `storage.set(key, ...)` и `window.location.reload()`.
- **Сметы в Excel** `exportEstimatesXls` — CSV (открывается в Excel) со сводкой всех смет: название, телефон, адрес объекта, тип, площадь, дата, вид (основная/ДС), статус, кол-во позиций, сумма клиенту.
- Раздел `_backupSections` (реестр ключ↔бэкап-ключ) в App.jsx; логика покрыта round-trip проверкой (scratchpad). Реализация НЕ трогает существующие авто-снимки рабочего пространства (WORKSPACE_BACKUPS_KEY) — они рядом, отдельным блоком.

## Клиентский кабинет: приватность + история (фиксы аудита)
- **Утечка замечаний устранена**: `publishProgress` перечитывал ноду и возвращал `clientRemarks` даже при `clientVis.remarks===false` (текст оставался в сыром JSON публичной ссылки). Теперь re-read замечаний только при `showRemarks`; при скрытых — принудительно `[]`, а существующие сначала синкаются в производство (не теряются).
- **Журнал пишется атомарно**: `_appendAuditEntry` использует Firebase `runTransaction` на ключе месяца — одновременные записи не затирают друг друга (резерв — обычная запись).
- **История для клиента** (публичный кабинет, вариант «безопасная лента»): собирается на лету в `PublicProgress` из снимка — старт работ, завершённые этапы (по `stage.factEnd`), принятые оплаты (сумма+дата, из `snap.payments`), выполненные замечания, сдача, обновление сообщения. Себес/маржа/подрядчики НЕ попадают. Двойной гейт видимости: скрытый раздел не кладётся в снимок И пропускается в цикле. Снимок дополнен: `stage.factEnd` и `payments:[{date,amount}]` (только income по договорам объекта, только при `showPay`).
