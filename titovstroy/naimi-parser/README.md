# Парсеры мастеров Naimi.kz и OLX.kz → база TitovStroy

Собирает мастеров/рабочих с **Naimi.kz** и **OLX.kz** и пишет их только в отдельные ключи
`titovstroy-masters`, `titovstroy-masters-olx` и два ключа настроек. **Объекты, сметы,
финансы, договоры, производство, клиенты и подрядчики не затрагиваются.**

## Как это устроено
- Список мастеров и справочники берутся **напрямую с публичного JSON-API naimi** — без браузера.
  Это быстро (секунды) и стабильно. Город передаётся заголовком `App-City` (слаг: `almaty`, `karaganda`…).
- Эндпоинт списка: `GET pub/catalogue/categories/work/specialists?slug={услуга}&limit=&page=&review_filter=`.
- Данные нормализуются, дедуплицируются (один мастер — несколько услуг объединяются) и пишутся в
  базу в формате, который читает CRM (узел = строка с JSON, поле `items[]`).
- Общая категория OLX автоматически разворачивается в полный текущий список из 20 строительных
  специальностей. Категории с лимитом выдачи 1000 дополнительно обходятся по городам.
- Каждый источник выполняется отдельной параллельной задачей GitHub Actions, поэтому сбой или
  долгий ответ одного сайта не лишает времени второй сайт.
- Список каждый запуск собирается заново. Живые поля обновляются, старые телефоны сохраняются,
  исчезнувшие из текущей выдачи записи не удаляются, а получают `active: false`.

## Управление из сервиса (без токенов)
Раздел «🔎 Мастера» в CRM (у Админа) → блок **«⚙️ Настройки обновления»**: частота
(Выключено / Раз в день / 2 раза / Раз в неделю), города, категории, телефонов за прогон, и кнопка
**«🔄 Обновить сейчас»**. Настройки пишутся в ключ базы `titovstroy-masters-config`.

Workflow проверяет настройки **каждые 10 минут**, но каждый парсер сам решает, парсить ли
сейчас (по частоте / по кнопке «Обновить сейчас»). Если не пора — прогон завершается за секунды.
Поэтому «Обновить сейчас» обычно срабатывает в течение 10–30 минут с учётом очереди GitHub.
Ручной запуск с самого GitHub (**Actions → Run workflow**) парсит всегда, игнорируя частоту — для теста.

## Разовая настройка (один раз, ~5 минут)

### 1. Сервисный аккаунт Firebase (ключ для записи в базу) — ОБЯЗАТЕЛЬНО
1. Firebase Console → ⚙️ **Project settings** → вкладка **Service accounts**.
2. Кнопка **Generate new private key** → скачается JSON-файл.
3. Открыть его **обычным текстовым редактором** (Блокнот/VS Code), выделить всё (Ctrl+A), скопировать.
4. В репозитории GitHub: **Settings → Secrets and variables → Actions → New repository secret**:
   - **Name:** `FIREBASE_SERVICE_ACCOUNT`
   - **Secret:** вставить **всё содержимое** JSON-файла (должно начинаться с `{` и `"type": "service_account"`).

> Вставлять именно как есть, без табов/переносов из таблиц — иначе `JSON.parse` упадёт.
> Этот ключ даёт запись в базу — храните только в Secrets, никуда не коммитьте.

### 2. (необязательно) Переменные
**Settings → Secrets and variables → Actions → Variables**. Всё имеет безопасные значения по
умолчанию, задавать не обязательно:
| Переменная | Зачем | По умолчанию |
|---|---|---|
| `FB_DB_URL` | URL базы | боевая `titovstroy-da1cf` |
| `MASTERS_KEY` | ключ в базе | `titovstroy-masters` |
| `MAX_PAGES` | предел пагинации на услугу | `20` |

Слаги городов: `almaty`, `astana`, `shymkent`, `karaganda`, … (полный список отдаёт
`https://apipub.naimi.kz/app/pub/reference/city/list`). **Только латиница.**

### 3. Первый запуск (проверка)
1. GitHub → вкладка **Actions** → workflow **«Парсеры мастеров (naimi + OLX)»** → **Run workflow**.
2. В логе: строки `+N новых (получено M)` по каждой услуге и `ИТОГО уникальных мастеров: N`.
3. Дальше он идёт по расписанию из настроек CRM.

## Телефоны — нужна сессия naimi (важно)
Номер телефона naimi отдаёт **только авторизованным**: запрос `pub/call/specialist` без сессии
возвращает `Access denied`. Открытого способа получить номер нет. Поэтому:

- **Без сессии** парсер просто **пропускает телефоны** (в логе: «телефоны: пропуск — нет секрета
  NAIMI_SESSION»), прогон при этом успешный, база наполняется мастерами.
- **Чтобы включить телефоны**, добавьте сессию своего аккаунта naimi как секрет:
  1. Зайдите на **naimi.kz** под своим аккаунтом (вход по коду из SMS).
  2. Откройте **DevTools → Network**, найдите любой запрос к `apipub.naimi.kz`,
     в его **Request Headers** скопируйте значения `Api-Session` и (если есть) `Api-User`.
  3. Добавьте секреты: `NAIMI_SESSION` = значение `Api-Session`, `NAIMI_USER` = значение `Api-User`.
- Тогда парсер докапывает номер у `phonesPerRun` мастеров за прогон. Очередь сначала проходит всех,
  кого ещё не проверяли, затем возвращается к самым давним неудачным проверкам. Сессия может протухать —
  если в логе снова «Access denied», обновите секрет `NAIMI_SESSION`.

## Почему номер может отсутствовать
- Парсер гарантирует обход очереди, но не может создать номер, которого источник не публикует.
- OLX возвращает номер только для объявлений, где автор разрешил его показывать. `unavailable`
  означает, что источник ответил успешно, но номера нет; `retry` — временный сбой или ограничение,
  такой мастер будет проверен снова.
- Naimi требует действующую авторизованную сессию. Ошибка сессии показывается в настройках CRM и
  не маскируется под «номера нет».
- Ошибка чтения Firebase останавливает весь прогон до записи. Парсер никогда не заменяет существующую
  базу пустым списком из-за временного сетевого сбоя.

## Уважение к сайту / право
- **ToS/право:** naimi.kz — чужой ресурс со своими условиями использования и персональными данными
  людей. Использование — под вашу ответственность и только для внутренних нужд (поиск подрядчиков),
  не для перепродажи/рассылок.
- Паузы между телефонами не снижать агрессивно, `phonesPerRun` до сотен не задирать — смысл в постепенности.
