# Установка системы новой компании

Как поставить сервис компании-клиенту с нуля. Порядок шагов не случаен — часть
из них ломается, если поменять местами; такие места отмечены.

---

## Главное правило: одна компания — одна установка

В базе ключи называются просто `titovstroy-objects`, `titovstroy-estimates` — в них
**нигде не записано, чьи это данные**. Подмешать вторую компанию в ту же базу нельзя:
они увидят объекты, сметы и деньги друг друга.

Поэтому каждому клиенту — **своя база Firebase и свой проект Vercel**, из того же
самого репозитория. Код общий, данные и настройки раздельные.

Что это даёт: данные клиента физически отдельно (сильный аргумент на переговорах),
сломалось у одного — у остальных работает, клиент решил уйти — отдали ему базу.
Чем платим: обслуживать надо каждую установку отдельно. Правки кода уезжают во все
установки сами, а секреты и настройки у каждой свои.

---

## Что понадобится до начала

- аккаунт Google (для Firebase) — можно свой, можно клиента;
- аккаунт Vercel;
- Telegram — чтобы завести бота;
- домен клиента или свой поддомен.

Полчаса-час на установку, если ничего не чинить по дороге.

---

## Шаг 1. База Firebase

1. console.firebase.google.com → **Add project**. Имя любое, Analytics не нужен.
2. Build → **Realtime Database** → Create Database. Регион — ближайший (europe-west1).
   Начать можно в **test mode**, правила поставим на шаге 5.
3. Project settings → **General** → пролистать вниз, «Your apps» → значок `</>`
   (Web) → зарегистрировать. Скопировать блок `firebaseConfig` — семь строк,
   они понадобятся на шаге 3.
4. Project settings → **Service accounts** → Generate new private key. Скачается
   JSON-файл. Из него понадобятся два поля: `client_email` и `private_key`.

> **Файл сервисного ключа — это полный доступ к базе мимо всех правил.** Не
> класть в репозиторий, не пересылать в мессенджерах. Только в переменные Vercel.

---

## Шаг 2. Telegram-бот

1. Написать [@BotFather](https://t.me/BotFather) → `/newbot` → имя и адрес бота.
2. Он выдаст токен вида `1234567890:AA...`. Сохранить, он нужен на шаге 3.
3. Бот одной компании **не годится** для другой: он хранит привязки чатов к
   сотрудникам. Каждой установке — свой бот.

---

## Шаг 3. Проект Vercel

1. vercel.com → **Add New → Project** → импортировать тот же репозиторий.
2. Root Directory указать `titovstroy` (если репозиторий подключается целиком).
3. **Environment Variables** — прописать до первой сборки:

| Переменная | Откуда | Зачем |
|---|---|---|
| `VITE_APP_ENV` | поставить `prod` | **Обязательно.** Без неё в шапке будет висеть «🧪 ТЕСТ · dev-база», а уведомления в Telegram молчать |
| `VITE_FB_API_KEY` | firebaseConfig | подключение к базе |
| `VITE_FB_AUTH_DOMAIN` | firebaseConfig | |
| `VITE_FB_DATABASE_URL` | firebaseConfig | |
| `VITE_FB_PROJECT_ID` | firebaseConfig | |
| `VITE_FB_STORAGE_BUCKET` | firebaseConfig | |
| `VITE_FB_SENDER_ID` | firebaseConfig `messagingSenderId` | |
| `VITE_FB_APP_ID` | firebaseConfig | |
| `FIREBASE_SA_CLIENT_EMAIL` | из JSON сервисного ключа | вход сотрудников, уведомления |
| `FIREBASE_SA_PRIVATE_KEY` | из JSON, переводы строк как `\n` | то же |
| `TELEGRAM_BOT_TOKEN` | от BotFather | уведомления |
| `PARSER_ALLOWED_ORIGINS` | адрес сайта клиента, напр. `https://crm.company.kz` | чтобы запуск рассылки нельзя было дёрнуть с чужого сайта |

Необязательные:

| Переменная | Зачем |
|---|---|
| `CRON_SECRET` | закрывает вход планировщика секретом. Без неё расписание всё равно работает — пускается только собственный планировщик Vercel |
| `TELEGRAM_WEBHOOK_SECRET` | мгновенные ответы бота на команды (`/start`, `/id`) |

4. Deploy.

---

## Шаг 4. Домен

Settings → Domains → добавить домен клиента (`crm.company.kz`) или свой поддомен.
Прописать у регистратора запись, которую покажет Vercel.

**После смены домена вернуться к `PARSER_ALLOWED_ORIGINS`** и указать там боевой
адрес, иначе кнопка «Отправить сейчас» и мгновенные уведомления будут получать отказ.

---

## Шаг 5. Правила базы — ПОСЛЕ первого входа, не раньше

Порядок здесь жёсткий, иначе можно закрыть вход всем, включая себя.

1. Открыть сайт. База пустая → вместо входа покажется **мастер первого запуска**:
   название компании и первый администратор. Заполнить.
2. Войти этим администратором. Убедиться, что всё открывается.
3. Дать войти **по разу каждому** заведённому сотруднику.
4. **Только теперь** опубликовать правила из `firebase/database.rules.json`
   (Firebase → Realtime Database → Rules → вставить → Publish).

Пока правила не опубликованы, база открыта. Не оставлять так дольше, чем нужно
на первые входы.

---

## Шаг 6. Что заполняет сам клиент

В Админке, по порядку:

1. **🏢 Реквизиты** — юрлицо: название, БИН, банк, счёт, директор, телефон.
   Отсюда договоры **и акты** берут исполнителя. Не заполнить — в акте вместо
   исполнителя будет прочерк.
2. **🎨 Оформление** — название, логотип, фирменный цвет, WhatsApp, печать,
   оформление КП.
3. **💰 Прайс-лист** — свои работы и цены. В системе есть базовый каталог
   (~150 позиций) как отправная точка, он правится под клиента.
4. **👥 Сотрудники** и **🔒 Права ролей**.
5. **🔔 Уведомления** — включить, подключить бота, отметить кому что слать.

---

## Шаг 7. Фоновые задачи (по желанию)

Всё в `.github/workflows/`. Нужны, только если клиенту это нужно:

- **Парсеры мастеров** (naimi + OLX) — поиск подрядчиков по Караганде. Другой
  компании обычно **не нужны, и это главный потребитель трафика**: 16 МБ из 17 МБ
  боевой базы — именно они. По умолчанию не включать.
- **Бэкапы** — ночная выгрузка базы. Полезны всем.
- **Уведомления** — запасной прогон раз в час. Основной путь живёт на Vercel и
  работает сам; этот нужен на случай, если Vercel недоступен.

Для бэкапов и запасных уведомлений нужны секреты репозитория:
`FIREBASE_SERVICE_ACCOUNT` (весь JSON целиком), `TELEGRAM_BOT_TOKEN`,
и переменная `FB_DB_URL`.

## Проверка, что всё встало

1. Открыть сайт — **нет метки «🧪 ТЕСТ»** в шапке. Есть — не задана `VITE_APP_ENV=prod`.
2. Завести тестовый объект, сменить ему статус → уведомление в Telegram приходит
   за несколько секунд.
3. Напечатать акт → в строке «Исполнитель» реквизиты клиента, а не чужие.
4. Открыть КП и кабинет клиента по публичной ссылке с телефона.
5. Админка → Проверка базы → нет ошибок.

## Деньги

| | Тариф | Сколько |
|---|---|---|
| Firebase | Spark (бесплатный) | 1 ГБ хранения, 10 ГБ скачивания в месяц. Чистая CRM без парсеров — около мегабайта на компанию, запас огромный |
| Vercel | Hobby бесплатно, **но только для личного некоммерческого использования** | Продаёшь внедрение — нужен Pro, ~$20/мес. Это за тебя, не за клиента: проекты живут в одном аккаунте |
| Telegram | — | бесплатно |
| GitHub Actions | бесплатно для публичных репозиториев | закроешь репозиторий — 2000 минут в месяц бесплатно, дальше платно |
| Домен | у клиента | или твой поддомен бесплатно |

**Прямых расходов на клиента — ноль.** Платишь один раз за Vercel Pro и своё время.

Что может вывести за бесплатный тариф Firebase: парсеры мастеров (на боевой базе
они давали сотни мегабайт трафика в сутки) и очень активная работа десятков
сотрудников. Следить — Firebase Console → Realtime Database → Usage.

## Чего пока НЕ хватает для чужой компании

Честный список, чтобы не выяснять это при клиенте:

1. **Себестоимость и наценка лежат в коде сайта.** Файл базового каталога работ
   собирается в страницу — любой, кто откроет исходники, увидит `cost` и `margin`.
   Свои цены клиент задаст, но исходные числа видны. Чинится выносом в закрытый
   узел базы.
2. **Репозиторий публичный.** Весь код открыт — продавать внедрение открытого кода
   тяжело. Закрыть его можно, но тогда Actions станут ограниченными.
3. **Юридический текст договоров — казахстанский**, под физлиц и ТОО. Другая
   юрисдикция потребует переписывания шаблонов.
4. **Домен публичных ссылок** (КП, кабинет клиента) — это домен установки. Если
   клиент захочет свой бренд в ссылке, домен должен быть его.
