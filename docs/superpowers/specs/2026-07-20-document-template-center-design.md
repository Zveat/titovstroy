# Центр шаблонов документов TitovStroy

Дата: 20 июля 2026 года  
Статус: дизайн согласован владельцем продукта

## 1. Цель

Перенести шаблоны договоров, дополнительных соглашений, приложений, актов выполненных работ, договоров дизайна, брони, подряда и других документов из `src/App.jsx` в отдельный управляемый раздел TitovStroy ERP.

Владелец должен иметь возможность создавать и редактировать шаблоны в простом встроенном редакторе уровня Word, не изменяя исходный код. Текущие способы выгрузки в PDF, Google Docs, DOCX и Excel должны продолжить работать.

## 2. Абсолютные ограничения

### 2.1. Юридический текст

Первичный перенос каждого существующего шаблона выполняется дословно.

- Нельзя сокращать, переписывать, улучшать или исправлять юридический текст.
- Нельзя менять смысл, формулировки, нумерацию пунктов, порядок разделов, таблицы, условия, реквизиты и состав документа.
- Нельзя автоматически исправлять орфографию, пунктуацию или стиль.
- Нельзя применять генеративное переписывание текста.
- Опубликовать первичную перенесённую версию можно только после автоматического и ручного сравнения с действующим документом.
- Последующие изменения юридического текста выполняет только пользователь через новую опубликованную версию.

### 2.2. Существующие данные

Разработка и миграция не должны изменять существующие объекты, сметы, договоры, дополнительные соглашения, АВР, финансы, клиентов, подрядчиков, производственные карточки и ранее сформированные документы.

- Автоматическая массовая перезапись существующих документов запрещена.
- Старые документы продолжают работать через текущие генераторы.
- Новые ноды шаблонов хранятся отдельно от рабочих сущностей.
- Подключение нового генератора выполняется отдельно для каждого типа документа.
- До приёмки нового типа текущий генератор остаётся единственным рабочим путём.

## 3. Выбранный подход

Используется встроенный структурированный редактор на базе проверенного движка TipTap/ProseMirror или совместимого редактора со схемой документа.

Шаблон хранится не как произвольный HTML, а как структурированный JSON редактора. Защищённые автополя являются отдельными атомарными узлами схемы. Пользователь может вставлять и перемещать их, но не может изменить их внутренний идентификатор или случайно повредить значение.

Один канонический шаблон используется для формирования всех поддерживаемых форматов. Отдельные копии юридического текста для PDF, Google Docs и DOCX не допускаются.

## 4. Интерфейс

### 4.1. Размещение

В Админке появляется раздел `Шаблоны документов`.

Основной экран содержит:

- поиск по названию;
- фильтр по категории и состоянию;
- список всех шаблонов;
- состояние `Черновик`, `Опубликован`, `Архив` или `Ещё в коде`;
- номер активной версии;
- дату и автора последнего изменения;
- действия `Открыть`, `Продолжить`, `Копировать`, `Архивировать`;
- кнопку `Новый шаблон`;
- переход к истории публикаций.

Согласованный Figma-макет: <https://www.figma.com/design/oJuV5dtRgWAryXO5aOeqEZ>

### 4.2. Создание шаблона

Новый шаблон создаётся:

- с чистого листа;
- копированием существующего шаблона.

При создании задаются название, категория, тип документа, места использования и поддерживаемые форматы выгрузки.

### 4.3. Редактор

Редактор отображает лист A4 и включает только необходимое базовое форматирование:

- отмена и повтор;
- шрифт и размер;
- полужирный, курсив, подчёркивание;
- выравнивание;
- заголовки;
- маркированные и нумерованные списки;
- таблицы;
- разрыв страницы;
- защищённые автополя.

Редактор не должен позволять вставку скриптов, произвольного CSS, iframe или небезопасной разметки.

### 4.4. Редактирование конкретного документа

После создания документа по объекту пользователь с соответствующим правом может изменить обычный текст только этого документа. Общий шаблон не изменяется. Защищённые автополя остаются заблокированными.

Каждое сохранение индивидуальных изменений создаёт новую версию экземпляра документа. Предыдущие версии не удаляются.

## 5. Жизненный цикл шаблона

Используется процесс `Черновик -> Предпросмотр -> Публикация`.

1. Обычное сохранение обновляет только черновик.
2. Черновик не влияет на создание рабочих документов.
3. Предпросмотр подставляет данные выбранного тестового объекта без записи в этот объект.
4. Перед публикацией выполняется валидация обязательных автополей и поддерживаемой структуры.
5. Публикация создаёт новую неизменяемую версию.
6. Только опубликованная версия применяется к новым документам.
7. Откат не удаляет версии, а назначает ранее опубликованную версию активной.
8. Архивный шаблон не предлагается при создании новых документов, но его версии остаются доступными истории.

## 6. Защищённые автополя

Автополя отображаются в редакторе как визуально отличимые заблокированные элементы. У каждого поля есть стабильный машинный идентификатор и человекочитаемое название.

### 6.1. Группы полей

- Клиент: ФИО, ИИН, телефон, удостоверение личности, адрес регистрации, реквизиты юридического лица.
- Объект: уникальный ID, адрес, тип недвижимости, площадь, ответственный, даты работ.
- Договор: номер, дата, вид, сумма, сроки, статус.
- Смета: название, работы, количество, единицы, цены, скидки, итоги, таблица работ.
- Оплаты: график, внесённые платежи, задолженность, назначение платежа.
- Подрядчик: ФИО или наименование, ИИН/БИН, контакты, банковские реквизиты.
- Компания: наименование, БИН, адрес, банковские реквизиты, директор, логотип, печать и подпись.
- АВР: период, список выполненных работ, объёмы, суммы, стороны и основания.

### 6.2. Правила

- Значение автополя всегда берётся из рабочих данных, а не вводится в шаблоне.
- В шаблоне хранится только идентификатор поля и настройка отображения.
- Обязательное поле нельзя удалить без явного предупреждения.
- Публикация блокируется, если отсутствует обязательное для данного типа поле.
- Если рабочее значение не заполнено, формирование документа останавливается с точным списком недостающих данных.
- Табличные поля формируются из фактических строк сметы, АВР, оплат или работ.

## 7. Модель данных

Новые данные размещаются в отдельных ключах Firebase. Точные имена определяются планом реализации, но логические сущности обязательны.

### 7.1. Template

Содержит:

- `id`;
- `type`;
- `name`;
- `category`;
- `status`;
- `activeVersionId`;
- `supportedExports`;
- `usageContexts`;
- `createdAt`, `createdBy`, `updatedAt`, `updatedBy`.

### 7.2. TemplateVersion

Неизменяемая опубликованная версия содержит:

- `id`;
- `templateId`;
- `versionNumber`;
- `contentJson`;
- нормализованный текст для проверки равенства;
- список автополей;
- стили страницы;
- контрольную сумму содержимого;
- `publishedAt`, `publishedBy`;
- ссылку на предыдущую версию;
- результаты проверки экспортов.

Черновик хранится отдельно и может обновляться без создания опубликованной версии.

### 7.3. DocumentSnapshot

Новый сформированный документ получает неизменяемый снимок:

- `documentId`;
- `objectId`;
- `templateId`;
- `templateVersionId`;
- `contentSnapshot`;
- `variablesSnapshot`;
- итоговое каноническое представление;
- `createdAt`, `createdBy`;
- история индивидуальных версий документа.

Изменение или откат общего шаблона никогда не изменяет `DocumentSnapshot`.

### 7.4. Legacy-документы

Существующим документам не присваиваются новые снимки массово. Они получают логический режим `legacy` и продолжают использовать действующий генератор. Возможная конвертация старого документа выполняется только отдельным явным действием пользователя и не входит в первичную реализацию.

## 8. Формирование и экспорт

### 8.1. Общий конвейер

1. Выбрать активную опубликованную версию для типа документа.
2. Проверить структуру шаблона и обязательные автополя.
3. Собрать данные объекта без изменения рабочих сущностей.
4. Подставить значения.
5. Сохранить `DocumentSnapshot`.
6. Сформировать каноническое представление документа.
7. Передать его адаптерам PDF, Google Docs и DOCX.

Excel-выгрузка смет остаётся на текущем структурированном механизме и не переводится в текстовый редактор.

### 8.2. Требование равенства

PDF, Google Docs и DOCX одного экземпляра должны содержать одинаковый юридический текст, порядок разделов, таблицы, значения, итоги и реквизиты. Форматные различия допускаются только там, где они неизбежны для конкретного формата и не влияют на содержание.

### 8.3. Резервный путь

Текущий генератор остаётся резервным до полной приёмки конкретного типа документа.

- Если новый шаблон не включён, используется только текущий генератор.
- Если опубликованный шаблон повреждён или недоступен, система не должна молча создавать неполный документ.
- До сохранения снимка допустим явный переход на старый генератор с сообщением пользователю.
- После сохранения снимка повторная выгрузка использует снимок и не переключается на другой шаблон.

## 9. Права доступа и аудит

По умолчанию управление шаблонами доступно только администратору.

В матрицу прав добавляются отдельные разрешения:

- просмотр шаблонов;
- создание и редактирование черновиков;
- публикация;
- откат версии;
- архивирование;
- редактирование конкретного документа.

Все критичные действия записываются в audit log:

- создание шаблона;
- изменение черновика;
- публикация;
- откат;
- архивирование;
- изменение конкретного документа;
- неудачная проверка или экспорт.

## 10. Резервное копирование и восстановление

Полный бэкап должен включать:

- карточки шаблонов;
- черновики;
- опубликованные версии;
- активные версии;
- снимки новых документов;
- историю индивидуальных изменений.

Восстановление шаблонов проходит через существующий защищённый облачный механизм восстановления. Восстановление не должно менять рабочие объекты и старые документы. Перед перезаписью каждого раздела создаётся подтверждённый облачный пред-бэкап.

## 11. Поэтапное внедрение

### Этап 1. Основа

- отдельный модуль шаблонов;
- редактор;
- автополя;
- черновики и версии;
- права;
- аудит;
- бэкап;
- конвейер снимков и адаптеры экспорта;
- feature flag на каждый тип документа.

### Этап 2. Договор ремонта и дополнительные соглашения

- дословный перенос;
- сравнение со старым генератором;
- проверка на нескольких реальных копиях данных в тестовой базе;
- включение только после приёмки.

### Этап 3. Дизайн и бронь

- договор дизайна;
- дополнительные документы дизайна;
- договор бронирования;
- те же проверки равенства.

### Этап 4. Подряд и АВР

- договор подряда;
- приложения подряда;
- АВР;
- те же проверки равенства.

### Этап 5. Остальные документы и завершение

- инвентаризация оставшихся генераторов;
- перенос каждого типа по той же процедуре;
- удаление дублирующего юридического текста из кода допускается только после полной приёмки всех экспортов и отдельного решения владельца.

## 12. Проверка качества

### 12.1. Автоматические тесты

- сериализация и загрузка структурированного шаблона;
- запрет изменения идентификатора защищённого поля;
- валидация обязательных полей;
- черновик не влияет на активную версию;
- публикация создаёт неизменяемую версию;
- откат меняет только активную версию;
- снимок документа не меняется после публикации нового шаблона;
- одинаковые данные передаются всем экспортным адаптерам;
- повреждённый шаблон не создаёт документ;
- права доступа проверяются в интерфейсе и в центральном write-gate.

### 12.2. Проверка юридического текста

Для каждого первично переносимого шаблона создаётся эталонный набор результатов старого генератора.

Сравниваются:

- нормализованный полный текст;
- заголовки и нумерация;
- количество и порядок пунктов;
- таблицы и строки работ;
- суммы и реквизиты;
- обязательные автополя;
- PDF;
- Google Docs;
- DOCX.

Любое смысловое расхождение блокирует включение нового шаблона.

### 12.3. Ручная приёмка

- создание документа по тестовому объекту;
- изменение черновика;
- предпросмотр с реальными тестовыми данными;
- публикация;
- создание нового документа;
- индивидуальное изменение документа;
- повторная выгрузка после изменения общего шаблона;
- откат версии;
- работа при недоступной Firebase;
- проверка старого документа до и после выкладки.

## 13. Критерии готовности

Функция считается готовой для `main`, только если:

1. Ни одна существующая рабочая сущность не была массово изменена.
2. Юридический текст первого подключаемого типа перенесён дословно.
3. Старые документы открываются и экспортируются как до изменения.
4. Новый документ получает неизменяемый снимок.
5. Черновик, публикация, история и откат работают.
6. Защищённые автополя нельзя повредить обычным редактированием.
7. PDF, Google Docs и DOCX прошли содержательное сравнение.
8. Текущий генератор остаётся доступным резервом.
9. Бэкап и восстановление включают новые данные.
10. Изменение протестировано в Preview на копии боевой базы до выкладки в `main`.

## 14. Не входит в первичную реализацию

- массовая конвертация старых документов;
- изменение юридических формулировок;
- совместное редактирование несколькими пользователями в реальном времени;
- полноценная замена Microsoft Word или Google Docs;
- загрузка произвольных Word-файлов с автоматическим преобразованием в шаблон;
- удаление старых генераторов до полной приёмки.
